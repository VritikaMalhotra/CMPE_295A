## Introduction

Small open language models now run as tool-calling agents on laptops, phones and desktop apps. Families such as Qwen3, SmolLM3 and LFM2.5 are released from 0.6 to 4 billion parameters with tool calling built in and with on-device use as an explicit goal [@yang2025qwen3; @bakouch2025smollm3; @liquid2026introducing]. At 16 bits these models still strain the memory of the devices they target: a 4B model needs about 8 GB for its weights alone, against about 2.5 GB at llama.cpp's Q4_K_M format [@taheri2026small]. In practice they ship at about 4 bits per weight, as GGUF files run by llama.cpp, the engine behind Ollama and LM Studio [@gerganov2023llamacpp]. Quantization is therefore not an optional optimization for these agents; it is the form in which users meet them.

The common view that 4-bit weights are nearly free rests on aggregate scores. The largest quantization studies find 4-bit weight-only formats within a few points of 16 bits on knowledge and reasoning benchmarks [@kurtic2025give; @li2024evaluating]. Agents are different in two ways. First, an agent runs a loop in which every step is a model output that must parse into a valid call, and a wrong call changes every later step [@yao2023react]. Second, agent benchmarks tolerate errors: τ²-bench ends an episode only after ten failed tool calls, so an agent can fail more often and still finish the task. Jang et al. showed exactly this masking for 9B to 35B models on τ²-bench: 4-bit weights doubled the share of calls to nonexistent tools in the most affected cell while the task score did not change significantly [@jang2026flat]. For the 0.6B to 4B models that actually run on devices, the evidence is contradictory and coarse. One study finds tool use almost unaffected by 4-bit quantization [@dong2025can], while another reports Qwen3-0.6B falling from 62.3% to 16.8% on single-turn BFCL under Q4_K_M [@taheri2026small]. Both report single-turn or aggregate scores, so neither shows where in a multi-turn conversation the damage lands.

Three families of repair are available, and practitioners have no evidence to choose between them. Grammar-constrained decoding restricts the output so that every call is syntactically valid [@geng2023grammar; @dong2025xgrammar]. Added bits give some or all of the weights more precision, uniformly, by layer, or by step [@hu2026structure; @li2026dynamic]. Quantization-aware distillation (QAD) retrains the quantized model to imitate its full-precision version, and vendors such as NVIDIA and Liquid AI now ship models trained this way [@xin2026qad; @liquid2026qad]. Each family is evaluated with its own yardstick (syntactic validity, perplexity, aggregate scores), none has been tested on multi-turn agents at this scale, and the published QAD results lack the control that separates retraining under quantization from simply training longer.

This project builds an open testbed that measures quantization damage step by step and compares the three repairs on the same models, tasks and runtime. The testbed runs BFCL multi-turn [@mao2024bfcl] and τ²-bench-verified [@barres2026tau2; @cuadron2025saber] against llama.cpp's real 4-bit kernels on its CUDA and CPU backends. It logs every agent step, classifies each failed step by type (for example a call to an unknown tool, invalid arguments, a malformed call, or a direct answer where a call was needed), and compares every 4-bit configuration with its 16-bit reference on the same tasks and seeds. Four research questions guide the study:

- **RQ1.** Where does 4-bit damage concentrate in small-agent conversations, by step type and by conversation depth?
- **RQ2.** How do grammar-constrained decoding (R1), added bits (R2: uniform, layer-selective and step-selective) and QAD retraining (R3) compare, each with its control, on the same models and benchmarks?
- **RQ3.** Do repairs validated on overall scores fix the underlying failures, or only the score?
- **RQ4.** What does each repair cost to deploy (memory, latency, extra tokens and energy) on llama.cpp's real 4-bit code paths, CUDA and CPU, for the same GGUF files?

The first measurements, all development data excluded from the pre-registered tests, already show that the problem is real and uneven. On a fixed WikiText-2 text, the KL divergence of Q4_0 from BF16 is 1.5 to 5.4 times that of Q4_K_M and IQ4_XS for every model (for example 0.246 against 0.108 and 0.102 for Qwen3-0.6B on CUDA), and a format's damage differs between the CUDA and CPU backends. The two backends produce identical greedy outputs on 90.5% to 96% of 200 fixed prompts at BF16 but on only 53% to 67% at Q4_0, so the backend is a factor in the study rather than a detail. The BF16 references themselves span a wide range of competence: averaged over 501 tasks and four sampled seeds, episode success ranges from 1.0% (SmolLM3-3B) to 50.2% (LFM2.5-2.6B). A first damage map over all eighteen 4-bit cells shows step-failure amplification of up to 1.33× (SmolLM3-3B at Q4_0), no step-level change for Qwen3-4B in any format, and lower episode success under Q4_0 in every model; later chapters report these results in full.

The rest of this report is organized as follows. The remainder of Chapter 1 defines the scope and contributions of the study and reviews the state of the art. Chapter 2 presents the architecture of the testbed: its software components and the cluster infrastructure on which every reported number is measured.

## Proposed Areas of Study and Academic Contribution

### Scope

The study is bounded so that every comparison is paired and every configuration can be run to completion on the SJSU College of Engineering HPC cluster.

- **Models.** Six open models up to 4B parameters from three families: Qwen3-0.6B, Qwen3-1.7B and Qwen3-4B [@yang2025qwen3], SmolLM3-3B [@bakouch2025smollm3], and LFM2.5-1.2B-Instruct and LFM2.5-2.6B [@liquid2026introducing]. Each has a BF16 GGUF reference.
- **Formats.** Three 4-bit formats as the damage conditions: Q4_0 (pure), Q4_K_M and IQ4_XS (importance matrix); Q5_0, Q6_K and Q8_0 and a layer-selective mix as the added-bits repairs; and QAD-trained Q4_0 files for the retraining repair.
- **Runtime.** llama.cpp at a pinned commit (d812350), on its CUDA and CPU backends from the same GGUF files, through the raw completion endpoint with one slot and prompt caching off.
- **Benchmarks.** BFCL multi-turn (base, missing-function and missing-parameter categories, 100 tasks each) and the 201 τ²-bench-verified tasks whose gold actions write to the database, scored by the official checkers. Each task runs four sampled trials with fixed seeds and one greedy pass per configuration, 2,505 episodes per configuration.
- **Out of scope.** Batched server engines such as vLLM, models above 4B parameters, activation and KV-cache quantization, and vision-language agents (an optional extension for CMPE 295B).

### Contributions

The project makes four contributions:

1. **A step-level damage map (RQ1).** For each model and 4-bit format, the amplification ratio of every failure type relative to the 16-bit reference, by step type and by conversation depth, with confidence intervals from a paired cluster bootstrap over tasks.
2. **A controlled comparison of the three repair families (RQ2 to RQ4).** Each repair is paired with its control (a grammar against the unconstrained baseline, added bits at a matched memory budget, QAD against a train-longer control at full precision), evaluated on failures as well as on scores, and costed in memory, latency, extra tokens and energy on both backends.
3. **An open testbed and step-log dataset.** The code, configurations, model manifests and every step record, so that any classifier revision or new analysis can be recomputed without rerunning a model.
4. **A pre-registered analysis plan.** Hypotheses, primary outcome, tests, multiple-comparison correction and exclusion rules fixed on OSF before the confirmatory runs [@nosek2018preregistration].

### Why It Matters

On-device agents trade memory, energy and latency against reliability, and today that trade is made blind. App developers need to know whether a 4-bit agent fails more often and, if so, which repair fits their memory and latency budget. Vendors who ship retrained quantized models need step-level validation with the control their published evaluations lack. Runtime maintainers gain per-format damage maps, grammar overhead figures and reproducible failing cases on llama.cpp's real kernels. Benchmark designers gain evidence of how error budgets hide damage. The results are aimed at a systems venue such as EuroMLSys, whose call covers compression, LLM optimization, agentic systems and benchmarking [@euromlsys2026workshop].

## Current State of the Art

This review covers weight quantization of small language models and the three repair families, tool-calling agents and their benchmarks, and the evaluation methodology the study depends on. We searched the ACM Digital Library, IEEE Xplore, the ACL Anthology, arXiv and the NeurIPS, ICML, ICLR and MLSys proceedings, and added the technical reports, model releases and runtime documentation through which industry ships quantized models.

### Quantization Formats and Measured Damage

Post-training quantization methods for language models follow two strategies. One protects the few weights that dominate the error: LLM.int8() keeps emergent outlier dimensions in 16 bits [@dettmers2022llmint8], AWQ rescales the roughly 1% of salient channels before rounding [@lin2024awq], and SpQR stores outliers in a sparse higher-precision structure [@dettmers2024spqr]. The other reduces the error of rounding everything, as GPTQ does with second-order compensation [@frantar2023gptq] and QuIP# with incoherence processing and lattice codebooks [@tseng2024quip]. These methods were developed mostly on models of 7B parameters and more, and the SpQR authors note that 3 to 4-bit quantization hurts the 1B to 10B range suited to edge devices most [@dettmers2024spqr].

The formats small models actually ship in are simpler. llama.cpp's Q4_0 rounds each block of 32 weights to 4 bits with one shared scale; its k-quants group blocks into 256-weight super-blocks, and the Q4_K_M recipe keeps selected tensors at 6 bits; i-quants such as IQ4_XS use non-uniform levels, and an importance matrix computed on calibration text can weight the rounding error [@gerganov2023llamacpp]. Model vendors now publish their own 4-bit builds: Google released Gemma 3 checkpoints trained for Q4_0 [@yvinec2025gemma], Liquid AI released QAD-trained Q4_0 files for LFM2.5 [@liquid2026qad], and Apple compresses its roughly 3B-parameter on-device model to 2 bits per weight [@apple2025apple]. Because the same "4-bit" label covers different block sizes, scale types and mixed-precision recipes, our testbed treats the format itself as an experimental factor.

Aggregate scores hide much of this damage. Dutta et al. count answers that flip between correct and incorrect and find that most schemes flip up to 13.6% of answers while accuracy stays within 2% of the 16-bit model; they recommend reporting flips and KL divergence alongside accuracy [@dutta2024accuracy]. Perplexity misses losses on knowledge-intensive tasks [@jaiswal2024compressing], and multi-step reasoning tolerates quantization less than instruction following [@li2024evaluating]. Damage also grows as models shrink [@li2024evaluating; @dutta2024accuracy]. For agents, ACBench reports only 1 to 3% loss on tool use under 4-bit GPTQ and AWQ but 10 to 15% on real-world application tasks [@dong2025can], and Li et al. find that the per-step KL divergence between a 4-bit and a BF16 agent is low on most steps, with a small mode of rare but consequential steps [@li2026dynamic]. Together these results argue for measuring damage per step and per failure type against a full-precision reference.

### Repair by Added Bits

The oldest repair gives the sensitive parts of a model more bits. HAWQ assigns per-layer precision from Hessian information [@dong2019hawq], SqueezeLLM keeps sensitive weights in a sparse full-precision matrix [@kim2024squeezellm], and llama.cpp's Q4_K_M recipe and importance matrix are the deployed, heuristic form of the same idea [@gerganov2023llamacpp]. Hu and Ramachandran recently tested the premise causally on nine models from 0.5B to 8B parameters: spending the same extra bits uniformly recovered 21 to 52 points more of the 4-bit accuracy loss than restoring the best layers to 8 bits, even with oracle layer choice [@hu2026structure]. Their damage measure, however, was continuation scoring on knowledge and reasoning tasks, with no generation or agent tasks. A second line of work varies precision over time: Any-Precision LLM overlays several precisions in one model's memory [@park2024any], MoBiQuant routes each token to a precision [@wang2026mobiquant], and Dynamic Mixed-Precision Routing sends each step of an agent episode to a BF16 or a 4-bit copy of Qwen3, recovering most of the 4-bit loss on ALFWorld and WebShop with 40% of steps at full precision [@li2026dynamic]. That study keeps both copies in memory and reports modelled latency only. Whether step-selective bits beat uniform or layer-selective bits at a matched memory budget, on tool-calling benchmarks and with measured cost, is untested.

### Repair by Retraining

Quantization-aware training lets the weights adapt to the quantization grid. LLM-QAT distills from the full-precision model's own generations [@liu2024llmqat], BitDistiller and EfficientQAT push the approach to 2 and 3 bits [@du2024bitdistiller; @chen2025efficientqat], and QLoRA trains low-rank adapters over a frozen 4-bit base [@dettmers2023qlora]. Quantization-aware distillation has since become an industrial technique. NVIDIA trains NVFP4 students on the KL divergence to their BF16 teacher and shows that plain QAT damages models post-trained with reinforcement learning while QAD recovers them [@xin2026qad]; Google's QAT for Gemma 3 reports a 54% smaller perplexity drop at Q4_0 [@yvinec2025gemma]; Liquid AI's QAD closes 48.4% to 73.4% of the BF16-to-Q4_0 gap for four LFM2.5 models [@liquid2026qad]; and Multiverse Computing distills a compressed MXFP4 student from its uncompressed original [@ryskulov2026healing]. Three gaps matter for agents. Every evaluation reports aggregate scores, and the single agent result uses the τ²-bench pass rate that can stay flat while failures grow [@ryskulov2026healing; @jang2026flat]. None includes a control that trains a full-precision model for the same steps and then quantizes it, although NVIDIA describes QAT as effectively an additional post-training stage [@xin2026qad] and the compute-optimal split between full-precision training and QAT shifts with the budget [@dremov2026compute]. And training costs for small models are not reported in usable terms.

### Repair by Restricting Output: Grammar-Constrained Decoding

Grammar-constrained decoding masks, at each decoding step, every token that would violate a formal grammar, so the output is valid by construction. Willard and Louf compiled grammars into a finite-state index over the vocabulary, the basis of Outlines [@willard2023efficient]; Geng et al. showed that input-dependent grammars let a model solve structured tasks without fine-tuning [@geng2023grammar]; and XGrammar prechecks context-independent tokens to make masking nearly free in co-designed serving engines [@dong2025xgrammar]. llama.cpp exposes the same mechanism through GBNF grammars and converts JSON schemas to grammars in its server [@gerganov2023llamacpp], and commercial APIs now guarantee schema adherence for function calls [@openai2024introducing].

The repair is cheap in the best engines but not free everywhere. In XGrammar's evaluation, llama.cpp's grammar engine was among the baselines slowed by preprocessing and per-token processing [@dong2025xgrammar], and JSONSchemaBench found that six frameworks differ in efficiency, schema coverage and output quality on 10,000 real schemas [@geng2025jsonschemabench]. Constraints also change what the model says: greedy masking distorts the model's distribution [@park2024grammar], and strict formats degrade reasoning [@tam2024let]. What a grammar fixes is narrow and exact. A grammar that lists the available tools makes a call to a nonexistent tool impossible, removing by construction the failure Jang et al. found amplified [@jang2026flat], and it guarantees well-typed arguments. It cannot choose the right tool among valid ones, supply the right value, decide when to stop or follow a policy, and it may turn a recoverable "tool not found" error into a silent valid-but-wrong call, the kind SABER identifies as decisive at state-changing steps [@cuadron2025saber]. Whether grammars remove damage or only relabel it is the question of RQ3. TSCG works on the input side instead, compiling JSON tool schemas into compact text and lifting small models' tool-use accuracy substantially [@sakizli2026tscg]. Neither TSCG nor any grammar engine has been evaluated on quantized agents.

### Agent Benchmarks and Evaluation Methodology

Tool use turned language models into agents: Toolformer learned when to call an API [@schick2023toolformer], Gorilla and ToolLLM scaled API calling [@patil2024gorilla; @qin2024toolllm], and ReAct established the reason, act, observe loop agents still run [@yao2023react]. Running this loop on the user's device is now a design goal [@erdogan2024tinyagent; @paramanayakam2025less]. Tool-use benchmarks have moved from single calls to stateful conversations. BFCL scores individual calls by abstract-syntax-tree matching [@patil2025berkeley], and its multi-turn set checks the environment state and the response after every turn, returns execution errors to the model, and cuts off a turn after 20 steps [@mao2024bfcl]. τ-bench added an LLM-simulated user, a domain policy and the pass^k metric [@yao2025taubench]; τ²-bench adds a telecom domain in which the simulated user also acts on the shared state [@barres2026tau2]; and Amazon's audit released τ²-bench-verified, which corrects tasks whose expected actions contradicted the policy or the database [@cuadron2025saber; @amazon2025tau2]. Table 1 compares the benchmarks we considered.

Table: Table 1. Agent benchmarks compared on the properties that matter for measuring quantization damage.

| Benchmark | Multi-turn | Simulated user | Main metric | Error tolerance | Used here |
|---|---|---|---|---|---|
| BFCL single-turn | No | No | AST or execution match | None; one call scored | No |
| BFCL V3 multi-turn | Yes | No (scripted turns) | State and response checks per turn | Errors returned; 20-step cap per turn | Yes |
| τ-bench | Yes | Yes (LLM) | Final database state; pass^k | Errors returned; step cap | No |
| τ²-bench | Yes | Yes (LLM, can act) | Final state and assertions; pass^k | Ends after 10 failed calls | Through verified |
| τ²-bench-verified | Yes | Yes (LLM, can act) | As τ²-bench, corrected tasks | As τ²-bench | Yes |
| ToolBench | Multi-step, one query | No | LLM-judged pass and win rate | Not applicable | No |
| AgentBench | Yes (environment turns) | No | Per-environment score | Varies | No |

The error-tolerance column is where quantization damage hides. In Jang et al.'s study, no change in final τ²-bench score survived multiple-comparison correction, yet 4-bit weights amplified failures the models already made at full precision; shrinking the error budget from ten failures to two re-exposed a 17-point gap in the affected cell [@jang2026flat]. Failure taxonomies show why a single score is not enough: MAST annotated multi-agent traces into 14 failure modes [@cemri2025why], Xu et al. separate tool-selection from tool-usage hallucinations [@xu2025reducing], and SABER finds that deviations at state-changing steps decide task success while read-only deviations barely matter [@cuadron2025saber].

Agent benchmarks are also small and noisy, and the methodology has to account for it. Miller recommends clustered standard errors, paired per-item comparisons and power analysis for model evaluations [@miller2024adding]; Dror et al. give a protocol for choosing significance tests in NLP [@dror2018hitchhikers]; and equivalence tests support "no change" claims [@lakens2017equivalence]. Many contrasts require correction, by Holm's procedure for confirmatory families [@holm1979simple] or false-discovery-rate control for screening [@benjamini1995controlling]. Inference is not reliably deterministic either, because kernels are not batch-invariant [@he2025defeating], so trials must be repeated and runtime settings pinned. Pre-registration guards against choosing the analysis after seeing the data [@nosek2018preregistration] and has been adopted in machine learning [@bertinetto2021neurips; @pineau2021improving].

### Summary and Research Gap

Table 2 places the three repair families against our setting. Each has been judged by a different yardstick, none on multi-turn agents at 0.6B to 4B parameters, and none with deployment cost measured on the runtime these models ship on.

Table: Table 2. Prior work on the three repair families compared with this project's setting.

| Repair family | Representative work | Evaluated on | Models and runtime | Gap this project addresses |
|---|---|---|---|---|
| R1 Restrict output | Outlines, XGrammar, llama.cpp GBNF, TSCG | Syntactic validity, throughput, tool-call accuracy | Unquantized models; server engines | Effect on quantized agents; removes failures or only relabels them; per-token cost on llama.cpp CUDA and CPU |
| R2 Add bits | Q4_K_M, SpQR, SqueezeLLM; layer-selective vs uniform; step routing | Perplexity, continuation scoring; ALFWorld and WebShop success | 0.5B to 8B; vLLM or custom kernels; two copies in memory | Step vs layer vs uniform bits at a matched memory budget on tool-calling tasks, with measured memory and latency |
| R3 Retrain | LLM-QAT, EfficientQAT; QAD from NVIDIA, Google, Liquid AI, Multiverse | Aggregate scores; τ²-bench pass rate | 1B and above; NVFP4, MXFP4, GGUF Q4_0 | Train-longer control; failures by type; training cost for small models |
| This project | All three on the same models and tasks | Per-step failures by type and depth; success; cost | Six models, 0.6B to 4B; llama.cpp CUDA and CPU | – |

The only process-level study of quantized agents shows that aggregate scores cannot see the damage, but it covers 9B to 35B models on server GPUs and tests one prompt-based repair [@jang2026flat]. The single-turn and aggregate studies disagree on how large the damage is for small models [@dong2025can; @paramanayakam2025less; @taheri2026small]. No published work compares output restriction, added bits and retraining on the same small models and multi-turn benchmarks, tests whether a repair removes failures or only restores the score, or reports each repair's cost on llama.cpp. This project fills that gap.
